# Decisions log: android-widget-live-resize

## 2026-08-18 — Step 1 — SizeMode.Responsive candidate set uses only the 4 real declared minimums, never synthetic in-between sizes

Chose `WIDGET_RESPONSIVE_SIZES = {DpSize(128,48), DpSize(196,48), DpSize(256,60), DpSize(256,120)}` — the exact `minWidth`/`minHeight` values already declared across the 5 `widget_provider_info*.xml` files — instead of inventing extra "transition" candidates (e.g. a `180x110` midpoint). Because `SizeMode.Responsive` pins `LocalSize.current` to exactly one candidate from the set (never an arbitrary point), using only real, already-designed breakpoints guarantees every consumer (typography tokens, the new content dispatcher) only ever has to reason about 4 known, individually-verified combinations. A synthetic midpoint like `180x110` was tried on paper and rejected: it resolves `MEDIUM` under `resolveWidgetSizeClass` (typography) but would resolve `SMALL` under any width-primary content-dispatch scheme, i.e. bigger fonts inside the compact Small layout — a real clipping risk that only exists because a candidate was invented rather than reused from an already-designed layout.

## 2026-08-18 — Step 1/3 — Content-transform dispatcher does not reuse `rememberWidgetSizeClass()`

`WidgetTheme.kt`'s `resolveWidgetSizeClass` (SMALL if `width < 120dp OR height < 100dp`) is tuned for typography/spacing scaling and pre-dates this spec. Medium's own declared default (256×60) resolves `SMALL` under it, purely because its height (60dp) is below the 100dp threshold — this is pre-existing, harmless for typography (it's the exact font sizing Medium already ships with today), but would be a functional bug if reused to pick WHICH content composable renders: a freshly-placed, never-resized Medium widget would render `SmallWeatherWidgetContent` instead of `MediumWeatherWidgetContent`, a visible regression. The new `AdaptiveWeatherWidgetContent` (`WidgetComponents.kt`) therefore compares `LocalSize.current` directly against the real declared minimums (`width>=256 && height>=120` → Large, `width>=256 && height>=60` → Medium, else Small) instead of calling `rememberWidgetSizeClass()`. This is safe specifically because the `SizeMode.Responsive` candidate set (see above) never reports an arbitrary in-between size — `rememberWidgetTypography()`/`rememberWidgetSpacing()` are untouched, so already-shipped, already-verified font/icon/spacing behavior is unaffected by this spec.

## 2026-08-18 — Step 3b — Clock graphic itself needed a separate scaling mechanism from the rest of the widget system

Asked directly, the user clarified "escalado de los relojes" should include the clock face/text growing, not just the surrounding weather info (which already rescaled via the existing token system). The clock graphic — `AnalogClock`/`TextClock` views rendered through `AndroidRemoteViews` from `res/layout/widget_rtc_*.xml` — lives entirely outside the Glance composable tree, so it can't consume `WidgetTypography`/`WidgetSpacing` directly. Digital clock text scales via `RemoteViews.setTextViewTextSize(viewId, unit, size)`, a plain runtime call available well below `minSdk` 24. The analog clock's `AnalogClock` view has no equivalent runtime "set layout size" call available before API 31 (`RemoteViews.setViewLayoutWidth/Height` is S+-only) — rather than version-gating and leaving pre-S devices unscaled, 2 new layout XML resources (`widget_rtc_analog_clock_medium.xml`/`_large.xml`) were added with larger explicit `layout_width`/`layout_height` on the `AnalogClock` (the dial is a vector drawable, so it scales cleanly to whatever View bounds it's given), selected by `rememberWidgetSizeClass()` at `RemoteViews(...)` construction time — works identically on every supported API level.

## 2026-08-18 — Step 3b (correction) — Growing `AnalogClock`'s `layout_width`/`layout_height` alone does not grow the rendered dial/hands

`android.widget.AnalogClock` (the deprecated framework widget used here) does NOT scale its dial/hand drawables up to fill its View bounds. Per its AOSP `onDraw`, it only applies a `canvas.scale(...)` when the *available* space is **smaller** than the dial drawable's own intrinsic size (`availableWidth < dial.getIntrinsicWidth() || ...`) — i.e. it only ever shrinks-to-fit, never grows-to-fit. All 4 clock drawables (`clock_dial.xml`, `clock_hour_hand.xml`, `clock_minute_hand.xml`, `clock_second_hand.xml`) declare a fixed `android:width="65dp" android:height="65dp"` (with a shared `viewportWidth="100" viewportHeight="100"`), so giving the `AnalogClock` View a larger `layout_width`/`layout_height` (85dp/110dp) just left extra blank space around a dial/hands still rendered at their original 65dp — the user caught this directly by testing. Fix: added `_medium`/`_large` variants of all 4 drawables (`clock_dial_medium.xml` etc., generated via `sed` substituting only the `android:width`/`android:height` values to 85dp/110dp — pathData and viewport untouched, so the vector scales losslessly) and repointed `widget_rtc_analog_clock_medium.xml`/`_large.xml`'s `android:dial`/`hand_hour`/`hand_minute`/`hand_second` attributes to them. Takeaway for future widget work: a native View's `layout_width`/`layout_height` only bounds where a `Drawable` *can* draw, not what size it *actually* draws at — always check the specific View's own draw logic (especially deprecated/legacy framework widgets like `AnalogClock`) before assuming a layout-size change is sufficient.
